[Heading 1] 1. Product Goal and Scope
[Normal] Build one connected TMT operations platform where a known person keeps one identity while moving through acquisition, training, company internship, work contribution and later employment. The system must preserve a complete operational timeline instead of duplicating the person across modules.
[CodeBlock] UNKNOWN AUDIENCE
    ↓ becomes identifiable/contactable
PERSON + LEAD
    ↓
Bootcamp / Demo / Direct Training / LearningSpaces
    ↓
Training Engagement (optional)
    ↓ selection / eligibility
Company Internship (optional)
    ↓
Projects / Tasks / Evaluations / Stipend / Documents
    ↓
Completion / Experience / Employee (future)

[Heading 2] 1.1 V1 business outcomes
[List Bullet] Every identifiable candidate has one Person record and a complete timeline.
[List Bullet] Employees can manage assigned leads, bootcamps, demos, training, interns, tasks, documents and communications without seeing unrelated sensitive data.
[List Bullet] Training Intern and Company Intern are separate engagement types.
[List Bullet] Bootcamp is never a mandatory prerequisite for training enrollment.
[List Bullet] Company Intern work follows assign → submit → evaluate → revise/approve, with immutable activity history.
[List Bullet] Authorized users can generate a versioned letter once and deliver the same issued artifact through portal, email, WhatsApp or any combination.
[List Bullet] Payments, stipend and candidate fees remain separate financial domains.
[List Bullet] Founder/Admin receives an operational command center with cautions, private work, communications, finance and reports.
[Heading 1] 2. Reference Technology Architecture
[Normal] Use a modular monolith for V1. This is easier for interns to reason about, test and deploy while preserving strong module boundaries. Split into services later only when scale or organizational boundaries justify it.
[CodeBlock] apps/
  web/
  api/
modules/
  auth/ people/ leads/ bootcamps/ demos/ training/ internships/
  work/ evaluations/ payments/ stipends/ communications/ mail/
  documents/ certificates/ calendar/ notifications/ reports/ audit/
shared/
  permissions/ events/ files/ integrations/ validation/

[List Bullet] No module directly calls Razorpay/WhatsApp/SMTP/IMAP. It calls an integration adapter.
[List Bullet] Domain services own state transitions. Controllers/routes must not contain business rules.
[List Bullet] Background work uses durable queues. Sending or webhook retries must be idempotent.
[List Bullet] Use correlation IDs across API request → job → provider delivery log → audit event.

[Heading 2] 3.2 Duplicate management
[List Bullet] Before creating Person, normalize and compare phone and email against existing records.
[List Bullet] Possible duplicate must be suggested; do not silently merge.
[List Bullet] Authorized merge keeps a canonical Person and re-links leads, payments, documents, tasks, communications and engagements.
[List Bullet] Merge itself creates an immutable audit event containing source IDs, destination ID and actor.
[List Bullet] Never delete financial transactions, issued documents, certificate records or audit events during merge.
[Heading 1] 4. Authorization: Role + Permission + Scope + Context
[Normal] Do not implement pure role-based gating. Every sensitive request is evaluated using role, explicit permission, resource scope, assignment/ownership and field visibility.
[CodeBlock] ALLOW = hasPermission(user, action)
    AND scopeAllows(user, resource)
    AND contextAllows(user, resource)
    AND fieldPolicyAllows(user, requestedFields)

→ EXTENDED / PAUSED → COMPLETED / RESIGNED / TERMINATED

[Heading 1] 26. E2E Acceptance Scenarios
[Normal] A. Lead → Bootcamp → Demo → Training — Import lead; dedupe/create Person; call; book slot; generate/send pass; check in; record activation; attend; schedule demo; reminder; demo outcome; enroll 45-day program; part payment; outstanding visible.
[Normal] B. Direct Training without Bootcamp — Create identifiable lead/walk-in; directly create Training Engagement; no bootcamp/demo prerequisite validation; batch + fee plan + portal visible.
[Normal] C. Training → Company Internship — Training Intern completes configured milestones; marked eligible; Admin creates Company Internship; offer generated; sent by portal/email/WhatsApp; intern acknowledges; onboarding starts.
[Normal] D. Direct Company Intern — Person/application becomes Company Intern without Training Engagement; offer/onboarding/work lifecycle works.
[Normal] E. Company Work Evaluation — Assign project/task/subtask; intern submits; evaluator requests changes; resubmit; approve; completion activity immutable.
[Normal] F. Founder Private Task — Founder creates PRIVATE task with subtasks/reminders; another admin/employee direct API request cannot read it unless explicit policy says otherwise.
[Normal] G. Multi-Mailbox Access — Employee A granted careers mailbox; Employee B not granted; A can read/reply; B gets 403 and mailbox is absent from UI.
[Normal] H. Document + Social Evidence — Generate offer from versioned template; send same artifact via portal/email/WhatsApp; intern views/acknowledges/uploads signed copy; LinkedIn action request accepts URL+screenshot; employee verifies.
[Normal] I. Stipend Paid — Authorized user approves and records payout; Company Intern sees own payout; configured email/WhatsApp notification logs independent channel results.
[Normal] J. Payment Idempotency — Provider sends same webhook twice; only one transaction/allocation exists.
[Normal] K. Duplicate Person Merge — Two duplicate Persons discovered; authorized merge preserves leads/payments/docs/work/history and creates audit event.
[Normal] L. Bulk Bootcamp Operations — Select candidates; assign slot, generate passes and send communications; per-item successes/failures displayed; retry only failures.
[Normal] M. Certificate — Eligible completion; Admin issues certificate; QR/public token verifies safe data; revoke/reissue preserves history.
[Normal] N. Permission Revocation — Remove employee mailbox/document permission; current session immediately loses protected action/read access on next request.

[Heading 1] Final Implementation Principles
[Normal] 1. One Person, many historical engagements.
[Normal] 2. Bootcamp/demo are optional acquisition paths, never universal prerequisites.

--- TABLE 31 ---
Case | Required behavior
Duplicate lead/person | Suggest existing Person; create new Lead if same person has new opportunity.
Bootcamp full | Waitlist or reject slot; do not overbook unless authorized override with audit.
Duplicate check-in | Return existing attendance; no second record.
Demo no-show | Allow reschedule; retain original attempt/history.
Training pause/transfer | Do not erase original batch/progress history.
Payment webhook repeated | Idempotent success; no duplicate transaction.
Manual payment proof rejected | Retain proof/history; allow resubmission.
Task deadline extension | Original due date remains in activity; approved new due date becomes active.
Evaluator unavailable | Reassign with history; old evaluations remain attributed.
Document template edited | New version only; issued documents unchanged.
Email/WhatsApp failure | DeliveryLog failed + retry policy + caution after terminal failure.
Mailbox sync failure | Show mailbox health; retry safely; do not expose credentials.
User loses permission | Subsequent reads/actions blocked immediately; historical audit remains.
Person merge | Re-link data and audit; no destructive loss.
Intern exits early | Close/hand over work, revoke access, reconcile stipend/docs, retain history.
Bulk partial failure | Operation completes PARTIAL; retry only failed items.
